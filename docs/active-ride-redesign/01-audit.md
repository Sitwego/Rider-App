## TL;DR

- **Reanimated is 4.3.1, worklets 0.8.3, RN 0.85.3 with Fabric, plus native-stack.** Path B (`react-native-screen-choreography`) needs no upgrades, so the Prompt 2 spike can evaluate both paths.
- The active-ride sheet is rendered **above the navigator** by `ActiveRideSheetProvider`, not by the home screen. v2 has to gate the sheet's presentation as well as swap the screen.
- The map is under heavy camera control: a per-frame follow camera, a route-change camera, and a sheet-padding camera, all on one ref. The compact thumbnail must switch these off and use a fit-to-bounds camera instead.
- **Every driver location tick re-renders the active-ride context and writes to MMKV.** That conflicts with the planned C10 "no per-tick renders" rule, and `useActiveRideView` has to be built around it.
- Several things the flow assumes are missing: Remote Config, i18n, analytics, component testing (RNTL), E2E, a dev menu, a carousel, and a Reanimated driver-position shared value. See [Risks](#7-risks).

### Ride state: stream → store → hooks
**Store:** `useReducer` plus two contexts in `src/providers/ActiveRideProvider.tsx`, persisted to MMKV under `ACTIVE_RIDE_STORAGE_KEY`. The native `GeoEtaUtils.java` reads the same MMKV instance (`active_ride`) to get `ride_polyline.from_to`.
- **Actions:** `SET-ACTIVE-RIDE`, `UPDATE-ACTIVE-RIDE` (deep-merges `ride_polyline` and computes `frozen_wait_elapsed`), `REMOVE-RIDE`, `SET-RIDE-STATUS-UPDATE-KEYS`, `IS-RIDE-SEARCH-BUTTON-PRESSED`.
- **Hooks:** `useActiveRideState()` and `useActiveRide()`.
- **Shape:** `ActiveRideState` and `RideRequestData` are in `src/types/rideRequestTypes.ts`.

**Flow:**
1. **Request.** `RideEstimateSheet._onSendRequest` → `sendRideRequest` → `SET-RIDE-STATUS-UPDATE-KEYS`.
2. **Driver offers.** `LoadingSheet` → native `OfferingDriverEvent.java` (gRPC `streamNextDriverOfferEvent`) → JS `offeringDriverEvent`.
3. **Acceptance.** `useRidePollingEffect` → `useRidePolling` (`src/hooks/queries.ts`, React Query, 2 s interval, `GET get-accepted-ride-by-driver/{ride_id}/{driver_id}/ride-details`) → `SET-ACTIVE-RIDE`. That sets `ride_status = request_status`, `from_to = decode(p1)` and `driver_to_pickup_polyline = decode(p2)`.
4. **Lifecycle.** Native `RideEventStreamer.java` (gRPC) → JS `rideEvent` → `useRideEvents`:
   - `DriverArrivedEvent` → `Arrived`
   - `RideStartEvent` → `Inprogress`
   - `RideCancelEvent` → `REMOVE-RIDE`
   - `RideEndEvent` → `REMOVE-RIDE`, then navigate to `RatingScreen`
5. **Location.** `useLocationUpdates` → `SitwegoMainModule.start(rideId)` → `RpcStreamingService` (gRPC `watchDriverLocationChanges`) → `GeoEtaUtils.findCurrentPositionOnPolyline` → JS `locationChange`. The event carries lat/lng, bearing, speed, accuracy and timestamp, plus `dx`, `etaSeconds`, `isOnPolyline` and `remainingCoordinates` when available. The JS side dispatches **`UPDATE-ACTIVE-RIDE` on every tick**.

## 3. Map-ref consumers

**These break or misbehave when the map's frame changes.**

All of these share the single `mapRef` in `RideMapView` (`src/ui/screens/RiderHomeScreen.tsx`):

| # | Consumer | Call | Frame assumption |
|---|---|---|---|
| M1 | `onMapReady` | `setCamera({center: driverPoint ?? route[0], zoom 17, pitch calcDynamicPitch(17), heading 0})` | Fixed zoom 17, which is far too tight for a roughly 180 px thumbnail |
| M2 | `routeKey` effect (new route, including Accepted → Inprogress) | `animateCamera(..., 1000ms)` with `calculateLatOffset(start.lat)` | **Hand-tuned latitude offset for a full-screen map under a sheet** |
| M3 | `useFollowVehicleCamera` (`src/hooks/useFollowVehicleCamera.ts`) | `engageCamera` (1500 ms), `followTo` (800 ms, throttled to 500 ms, **called every frame** from `handleDriverFrame`), `getCamera()` sync | Follow-mode zoom 16–18 by distance, with pitch, and heading-up |
| M4 | `useSheetMapPadding` (`src/hooks/useSheetMapPadding.ts`) | `mapPadding` prop plus `animateCamera({center: driverPoint}, 600ms)` one frame after a snap | Bottom padding is `SCREEN_HEIGHT × clamp(detent, 0.3, 0.4) + gap`. That's meaningless inside a thumbnail. |

**Elsewhere:**
- **M5:** the searching map (a separate ref) → `animateCamera` on `offeringDriverEvent`. Not affected by v2.
- **M6:** `RidesFairEstimates.tsx` → `fitToCoordinates`. Pre-booking, not affected.
- **M7:** `TrackingDemo.tsx` → `setCamera`. Dev only and not mounted.

**Observations:**
- M2, M3 and M4 already push overlapping `animateCamera` calls onto the same map, and they cancel each other.
- In v2 compact mode, M1–M4 must be **suspended** and replaced by a throttled fit-to-bounds (driver plus next target).
- In expanded mode, M3 and M4 can resume, with padding derived from the new frame rather than the screen height.
- The `RideMapView` wrapper also applies `marginTop: insets.top`, which assumes a full-bleed map.

## 5. Lifecycle states and v2 scope

`RideRequestStatus` (`src/types/rideRequestStatus.ts`):
```ts
"New" | "Accepted" | "Inprogress" | "Completed" | "Canceled" | "Expired" | "Arrived" | "Waitingforrider" | "Failed"
```

What the client actually does with these:
- Today the UI branches only on `Inprogress` and `Arrived`. Everything else counts as "heading to pickup".
- **Searching isn't a status.** It's inferred from `ride_status_update_keys` being set while `rideData` is empty.
- **`Completed` and `Canceled` are never stored.** The end and cancel events dispatch `REMOVE-RIDE`, and the end event then navigates to `RatingScreen`.
- `Waitingforrider` is declared but not handled anywhere in the UI.

### Proposed v2 phase mapping
| Client state | v2 `phase` | Layout |
|---|---|---|
| `Accepted`, no driver location or ETA yet | `assigned` | **v2** |
| `Accepted` with a driver location | `arriving` | **v2** |
| `Arrived`, `Waitingforrider` | `arrived` | **v2** |
| `Inprogress` | `on_trip` | **v2** |
| Searching (inferred), `New` | n/a | Current UI (LoadingSheet and searching map) |
| `Expired`, `Failed` | n/a | Current UI |
| `Completed`, `Canceled` (reached through `REMOVE-RIDE`) | n/a | Existing handoff (Rating screen or idle) |

The pure mapping function is `toRidePhase(status, hasDriverLocation)`. It's built in Prompt 3 and must be unit-tested against every enum member.

## Appendix — Existing tracking rules (from `docs/Real_Time_Vehicle_Tracking.md`)

The prompt flow refers to "REALTIMETRACKING.md Smoothness Contract C1–C6". No such numbered contract exists. These are the rules as the tracking doc describes them, numbered so that Prompt 11 can add C7 onward:

- **C1.** The marker never animates directly between raw GPS points. All motion is along a 1-D "metres along the route" axis.
- **C2.** The display runs about one update (~2 s) behind reality, to allow interpolation.
- **C3.** Prediction decays over 10 s. After that the marker is marked stale and dims.
- **C4.** Error correction is frame-rate independent (`alpha = 1 − e^(−rate·dt)`). Errors over 100 m cause a single jump. More than 50 m off-route for 3 fixes switches to raw lat/lng.
- **C5.** Heading comes from the route geometry and rotates the short way. Movement under 3 m below 0.5 m/s counts as jitter.
- **C6.** No React renders per animation frame.

The doc's usage example (`driverPoint` taken from `ride_polyline.from_to[0]`) is out of date. The code now uses `driver_location`.
